# VITALEAF 실제 체험 계정·관리자 주문관리 설계

## 목표

Vercel 배포 환경에서 막혀 있는 Firebase 회원가입과 로그인을 정상화하고, 실제 Firebase 회원인 체험 계정으로 상품 탐색부터 목업 결제와 주문내역 확인까지 검증한다. 관리자는 같은 테스트 주문을 일반 주문과 구분해 조회하고 처리 상태와 배송 정보를 관리할 수 있어야 한다.

현재 단계에서는 실제 PG 승인, 환불, 택배사 API를 추가하지 않는다. 고객과 운영자가 전체 주문 흐름을 직접 확인하는 데 필요한 기능에 집중한다.

## 확인된 현재 상태

- 최신 Preview 배포의 회원가입 화면은 열리지만 헤더에 `사이트 인증 설정이 필요합니다. 관리자에게 알려 주세요.`가 표시된다.
- 이 메시지는 `NEXT_PUBLIC_FIREBASE_*` 필수값이 배포된 브라우저 번들에 없을 때 발생한다. 회원가입 폼 자체보다 Vercel 환경변수 범위와 재배포가 우선 문제다.
- `https://vitaleaf.vercel.app/signup`은 구버전 배포라 회원가입 경로가 404다.
- 현재 관리자 화면은 판매 상품, 임시 저장, CSV, 1:1 문의를 지원한다.
- 회원 주문은 `users/{uid}/orders/{orderNumber}`, 비회원 주문은 `guestOrders/{orderNumber}`에 저장된다.
- 관리자에게는 회원·비회원 주문을 통합해서 보는 화면과 주문 처리 상태 변경 기능이 없다.

## 채택한 접근

### 실제 Firebase 체험 계정

프론트엔드 전용 우회 로그인을 만들지 않는다. 실제 Firebase Email/Password 사용자를 만들고 일반 고객과 같은 회원가입, 로그인, 프로필, 장바구니, 주문 API를 사용한다. 그래야 Firebase 설정, 권한 규칙, 서버 주문 저장까지 한 번에 검증할 수 있다.

체험 계정의 UID는 서버 전용 Vercel 환경변수 `TEST_CUSTOMER_UID`에 저장한다. 회원 주문 API는 검증된 Firebase ID 토큰의 UID가 이 값과 일치할 때만 주문 문서에 `isTestOrder: true`를 기록한다. 브라우저가 보낸 테스트 여부는 신뢰하지 않는다.

체험 계정 비밀번호는 저장소, 브라우저 코드, Firestore 문서에 저장하지 않는다. 생성 후 사용자에게만 전달한다. 체험 계정에는 실제 개인 정보 대신 명확한 테스트 이름, 전화번호, 주소를 사용한다.

### 기존 주문 저장소 통합 조회

관리자 전용 API가 Firebase Admin SDK로 회원 주문 컬렉션 그룹과 비회원 주문 컬렉션을 조회한 뒤 표준 응답으로 정규화한다. 별도의 관리자용 주문 복제 컬렉션은 만들지 않는다. 주문 생성과 관리자 데이터 복제 사이의 동기화 오류를 피하고 기존 주문 구조를 유지하기 위해서다.

초기 운영량을 고려해 각 저장소의 최신 100건을 읽고 합쳐 최대 200건을 최신순으로 제공한다. 현재 단계에서 복합 커서와 검색 전용 인덱스를 추가하는 것보다 구현·운영 비용이 낮다. 주문량이 이 한도를 지속적으로 넘을 때 서버 페이지네이션을 별도 확장한다.

## 인증과 배포 설정

### Vercel

다음 공개값은 Preview와 Production 모두에 설정하고 변경 후 새 빌드를 생성한다.

- `NEXT_PUBLIC_FIREBASE_API_KEY`
- `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`
- `NEXT_PUBLIC_FIREBASE_PROJECT_ID`
- `NEXT_PUBLIC_FIREBASE_STORAGE_BUCKET`
- `NEXT_PUBLIC_FIREBASE_MESSAGING_SENDER_ID`
- `NEXT_PUBLIC_FIREBASE_APP_ID`
- `NEXT_PUBLIC_FIREBASE_MEASUREMENT_ID` (선택)
- `NEXT_PUBLIC_SITE_URL`

주문과 관리자 API에 필요한 다음 값은 서버 전용으로 유지한다.

- `FIREBASE_ADMIN_PROJECT_ID`
- `FIREBASE_ADMIN_CLIENT_EMAIL`
- `FIREBASE_ADMIN_PRIVATE_KEY`
- `FIREBASE_STORAGE_BUCKET`
- `GUEST_ORDER_LOOKUP_SECRET`
- `INQUIRY_TOKEN_SECRET`
- `TEST_CUSTOMER_UID`

값 자체는 로그, 문서, 커밋, 채팅에 출력하지 않는다. 존재 여부와 적용 환경만 확인한다.

### Firebase

- Authentication의 Email/Password 공급자를 활성화한다.
- Production 도메인과 고정 Preview 별칭을 Authorized domains에 등록한다.
- 체험 고객 계정을 생성한 뒤 UID를 `TEST_CUSTOMER_UID`로 등록한다.
- 관리자 Auth 계정과 같은 UID의 `admins/{uid}` 문서에 문자열 `role: "admin"`을 둔다.
- 현재 Firestore와 Storage 규칙 및 필요한 인덱스를 배포한다.

회원가입 성공 후 프로필 저장이 실패하면 기존처럼 생성 계정을 정리하고 구체적인 복구 메시지를 표시한다. 인증 설정 오류는 비밀번호 오류와 구분한다.

## 고객 체험 흐름

1. 체험 계정으로 로그인한다.
2. 홈, 카테고리, 검색, 건강 고민 메뉴에서 상품을 찾는다.
3. 상품 상세에서 구매 옵션과 수량을 선택한다.
4. 같은 옵션을 다시 담아 수량 유지·추가 선택을 확인한다.
5. 장바구니에서 숫자 입력으로 수량과 결제예정금액 변화를 확인한다.
6. 주문서에 테스트 배송 정보를 입력하고 목업 결제를 완료한다.
7. 주문 완료 화면에서 주문번호를 확인한다.
8. 마이페이지에서 방금 주문과 배송 정보를 확인한다.
9. 관리자 주문관리에서 같은 주문이 `테스트`로 표시되는지 확인한다.

실제 카드 승인이나 출금은 일어나지 않는다. 주문 완료 문구에도 목업 결제임을 유지한다.

## 주문 상태와 데이터

기존 초기 상태 `mock-received`를 유지하고 화면에는 `접수`로 표시한다. 추가 상태는 다음과 같다.

```ts
type OrderStatus =
  | "mock-received"
  | "preparing"
  | "shipped"
  | "completed"
  | "cancelled";
```

회원 주문과 비회원 주문에 다음 선택 필드를 추가한다.

```ts
type OrderOperations = {
  isTestOrder?: boolean;
  status: OrderStatus;
  shippingCarrier?: string;
  trackingNumber?: string;
  statusUpdatedAt?: Date;
  statusUpdatedBy?: string;
};
```

레거시 주문의 상태가 없거나 잘못됐으면 `mock-received`로 정규화한다. `shipped`로 변경할 때만 배송사와 송장번호를 필수로 한다. 실제 금융 처리가 없으므로 `cancelled`는 목업 주문 취소 표시일 뿐 환불을 의미하지 않는다.

## 관리자 주문관리

관리자 화면에 `주문 관리` 탭을 추가한다.

### 목록

- 회원·비회원 주문을 최신순으로 통합 표시한다.
- 주문번호, 주문일, 회원 구분, 고객명, 상품 요약, 총액, 처리 상태를 표시한다.
- 체험 주문은 `테스트` 배지로 구분한다.
- 주문번호와 고객명으로 현재 불러온 목록을 즉시 검색한다.
- 전체/테스트 주문과 접수/상품 준비/배송 중/완료/취소 상태를 필터링한다.
- 접수 상태 건수를 탭 배지로 표시한다.

### 상세와 변경

- 주문 상품, 옵션, 수량, 금액, 결제수단, 배송지, 배송메모를 확인한다.
- 처리 상태를 변경한다.
- 배송 중 상태에는 배송사와 송장번호를 함께 저장한다.
- 중복 저장을 막고 처리 중 버튼을 비활성화한다.
- 저장 성공·실패를 명확한 한국어 알림으로 표시한다.
- 목록 API와 변경 API 모두 화면 인증과 별도로 서버에서 ID 토큰과 `admins/{uid}.role == "admin"`을 다시 검증한다.

### 이번 범위에서 제외

- 실제 PG 승인·취소·환불
- 택배사 배송조회 API
- 매출 통계와 회계 보고서
- 대량 주문 상태 변경
- 고객 이메일·문자 알림

이 기능들은 실제 주문량과 결제 연동이 생긴 뒤 추가해야 효과가 크다. 현재 추가하면 설정과 장애 지점만 늘어난다.

## API 경계

### `POST /api/admin/orders`

관리자 인증 후 주문을 조회한다.

```ts
type AdminOrderListRequest = {
  action: "list";
};

type AdminOrderListItem = {
  source: "member" | "guest";
  ownerId: string | null;
  orderNumber: string;
  customerName: string;
  createdAt: string;
  itemSummary: string;
  total: number;
  status: OrderStatus;
  isTestOrder: boolean;
};
```

### `POST /api/admin/orders/detail`

`source`, `ownerId`, `orderNumber`를 받아 해당 문서를 다시 읽는다. 회원 주문은 `ownerId`와 저장된 `userId` 일치를 확인한다. 응답은 관리자에게만 전체 배송 정보를 제공한다.

### `POST /api/admin/orders/update`

허용된 상태값만 저장한다. 배송 중 상태는 공백을 제거한 배송사와 송장번호가 모두 있어야 한다. 현재 문서를 트랜잭션으로 다시 읽고 존재 여부와 소유 경로를 확인한 뒤 운영 필드만 갱신한다. 고객·상품·금액 필드는 이 API에서 수정하지 않는다.

오류 응답은 인증 필요, 관리자 권한 없음, 주문 없음, 입력 오류, 일시적 저장 실패를 구분하되 서버 자격 증명이나 내부 문서 경로는 노출하지 않는다.

## 보안과 개인정보

- 테스트 계정 여부는 서버가 UID로 결정한다.
- 관리자 API는 모든 요청에서 Bearer ID 토큰과 관리자 역할을 검증한다.
- 관리자 목록은 전화번호와 전체 주소를 내려주지 않는다. 상세 요청에서만 제공한다.
- 고객은 기존 규칙대로 본인 회원 주문만 읽을 수 있다.
- 비회원 주문은 주문번호와 휴대전화 검증을 거친 기존 조회 API만 사용한다.
- 관리자 주문 변경은 상태·배송사·송장번호·변경자·변경 시각으로 제한한다.
- 비밀번호, ID 토큰, Firebase Admin 키는 로그에 남기지 않는다.

## 오류 처리

- Firebase 공개 설정 누락은 회원가입 버튼을 눌러야 알게 하지 않고 기존 헤더 상태 메시지와 폼 오류로 안내한다.
- 서버 설정이 부족해 주문 저장이 불가능하면 장바구니와 주문서 입력값을 유지한다.
- 회원 주문과 비회원 주문 중 한 저장소 조회가 실패하면 관리자에게 일부 결과를 정상 결과처럼 보여주지 않고 재시도 안내를 표시한다.
- 주문 상태 저장 실패 시 화면의 기존 상태를 유지한다.
- 오래된 관리자 요청 응답이 새로 선택한 주문 상세를 덮어쓰지 못하게 요청 세대를 구분한다.

## 테스트

### 자동 테스트

- Firebase 공개 설정 누락과 인증 오류 메시지
- 테스트 UID와 일반 UID의 `isTestOrder` 서버 판정
- 브라우저가 보낸 테스트 플래그 무시
- 레거시 주문 상태 정규화
- 회원·비회원 주문 통합 정렬과 최대 건수
- 관리자 목록에서 개인정보 제외
- 관리자 상세 권한과 회원 주문 소유 경로 확인
- 허용 상태 변경과 잘못된 상태 거부
- 배송 중 상태의 배송사·송장번호 검증
- 일반 회원과 비로그인 사용자의 관리자 API 거부
- 관리자 탭 검색, 필터, 상세, 중복 저장 방지, 실패 복구

### 실제 브라우저 검증

- 체험 계정 로그인과 로그아웃
- 상품 탐색, 옵션 선택, 장바구니 중복 담기
- 수량 직접 입력과 총액 즉시 반영
- 목업 결제와 주문 완료
- 마이페이지 주문내역
- 관리자 로그인과 테스트 주문 확인
- 상태·배송 정보 변경 후 재조회
- 데스크톱과 모바일 핵심 흐름
- 콘솔 오류와 가로 넘침 여부

## 배포 순서

1. 인증 환경과 Firebase 설정의 누락 범위를 값 노출 없이 확인한다.
2. 테스트 우선으로 주문 데이터와 관리자 API를 구현한다.
3. 관리자 주문관리 UI를 구현한다.
4. 전체 테스트, 린트, Production 빌드를 통과한다.
5. Preview에 필요한 환경변수와 Firebase 설정을 적용한다.
6. 체험 계정을 만들고 `TEST_CUSTOMER_UID`를 등록한 뒤 Preview를 재배포한다.
7. 고객·관리자 실제 브라우저 흐름을 검증한다.
8. 검증 결과를 보고하고 승인된 변경을 GitHub와 Production에 반영한다.

## 완료 기준

- 배포된 사이트에서 회원가입, 로그인, 로그아웃이 동작한다.
- 사용자에게 실제 Firebase 체험 계정의 아이디와 비밀번호를 전달한다.
- 체험 계정으로 상품 탐색부터 목업 결제와 주문내역 확인까지 완료한다.
- 관리자 화면에서 해당 주문을 테스트 주문으로 식별하고 상태와 배송 정보를 변경할 수 있다.
- 일반 회원은 관리자 API나 다른 고객 주문에 접근할 수 없다.
- 자동 테스트, 린트, Production 빌드와 데스크톱·모바일 브라우저 검증 결과가 남는다.
