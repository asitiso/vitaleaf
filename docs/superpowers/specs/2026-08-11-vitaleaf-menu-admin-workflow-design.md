# 바이탈리프 메뉴·관리자 상품등록 개선 설계

## 목적

현재 바이탈리프 쇼핑몰의 모든 노출 메뉴가 실제 페이지 또는 검증된 상품 필터로 연결되게 한다. 관리자는 긴 단일 폼과 이미지 URL 복사 없이 단계별로 상품을 작성하고, 이미지를 직접 올리고, 임시저장·미리보기 후 판매 공개할 수 있어야 한다.

우선순위는 기능 수가 아니라 운영자의 실제 작업시간 단축과 입력 실수 감소다. 주문 ERP, 직원별 세부 권한, 매출 분석은 실제 주문 저장과 PG가 없는 현재 단계에서는 제외한다.

## 확정 범위

- 헤더, 메가메뉴, 모바일 메뉴, 푸터에 노출된 링크는 모두 실제로 동작한다.
- 베스트, 오늘의 특가, 건강 고민별, 선물세트, 성분 가이드, 카테고리, 연령별, 첫 구매 체험 메뉴가 의도한 결과를 보여준다.
- 브랜드 소개, 고객센터, 배송, 교환·반품 페이지를 실제 라우트로 제공한다.
- 상품 등록은 4단계 마법사로 제공한다.
- 이미지는 Firebase Storage에 드래그앤드롭 또는 파일 선택으로 직접 업로드한다.
- 대표 이미지 자동 지정, 순서 변경, 대체텍스트, 삭제, 진행률과 재시도를 제공한다.
- 작성 중 상품은 임시저장하고, 관리자 전용 미리보기 후 판매 공개한다.
- 상품 복제, 빠른 재고 변경, CSV 일괄등록은 유지·개선한다.
- 실제 PG 결제와 주문 저장은 이번 범위에 포함하지 않는다.

## 구조 결정

### 메뉴와 분류값의 단일 출처

`lib/navigation/storefront-menu.ts`와 상품 분류 상수를 단일 출처로 사용한다. 헤더·메가메뉴·모바일 메뉴·푸터와 관리자 상품 폼이 같은 카테고리, 건강 고민, 연령 값을 공유한다. 메뉴에는 라벨, 경로, 쿼리, 설명을 함께 두고 테스트가 모든 경로를 순회한다.

상품 목록은 URL 쿼리를 실제 필터 상태로 해석하고, 현재 메뉴에 맞는 제목·설명·제거 가능한 필터 칩을 표시한다. 성분 가이드는 일반적인 정보와 관련 상품 이동만 제공하며 질병 치료나 검증되지 않은 효능을 단정하지 않는다.

### 초안과 공개 상품 분리

- `products`: 판매 공개 상품. 기존 고객 화면이 계속 사용한다.
- `productDrafts`: 작성 중 초안과 공개 상품의 수정 초안. 관리자만 읽고 쓴다.

새 상품 화면을 열면 안정적인 초안 ID를 먼저 만든다. 자동저장은 디바운스하여 `productDrafts/{id}`에 저장한다. 공개 시 전체 검증을 통과한 데이터를 Firestore batch로 `products/{id}`에 저장하고 초안을 정리한다. 공개 상품 수정 중에는 기존 공개본이 계속 판매 화면에 남으며, 새 초안을 공개할 때만 교체된다. 판매중지는 공개 문서를 초안으로 보존한 뒤 `products`에서 제거한다.

### 이미지 저장

이미지는 `products/{productId}/{generatedFileName}` 경로에 저장한다. 업로드 전 JPEG, PNG, WebP, 최대 10MB를 검증한다. `uploadBytesResumable`로 진행률·취소·재시도를 제공하고, 성공한 파일만 상품 미디어에 반영한다.

새 표준 필드는 `media: { url, storagePath, alt, order }[]`로 한다. 기존 `thumbnailUrl`과 `images[]` 문서는 정규화 계층에서 계속 읽을 수 있게 유지한다. 새 저장은 호환 필드도 함께 계산하거나 안전한 마이그레이션을 제공한다. 삭제·초안 폐기 시 다른 상품에서 사용하지 않는 Storage 파일만 제거한다.

### 관리자 등록 마법사

1. 기본 정보: 상품명, 자동 생성 slug, 카테고리, 건강 고민, 요약 설명
2. 이미지: 드래그앤드롭, 대표 이미지, 순서, 대체텍스트
3. 성분·섭취 정보: 효능 요약, 반복 가능한 성분표, 섭취법, 원산지, 인증, 주의사항
4. 판매 정보: 가격, 정상가, 재고, 베스트·신상품·특가, 공개 전 점검

각 단계는 저장 상태를 표시하고 앞뒤로 자유롭게 이동한다. 오류는 해당 단계와 필드에 연결하고 첫 오류로 포커스를 이동한다. 모바일에서는 하단 고정 이전·다음·임시저장 버튼을 제공한다. 미완성 단계는 공개할 수 없지만 초안 저장은 허용한다.

### 관리자 대시보드

상품명·문서 ID·카테고리 검색, 공개/초안/품절 필터, 최근 수정순 정렬을 제공한다. 각 행은 이미지, 상품명, 상태, 가격, 재고, 마지막 저장 시각과 편집·복제·미리보기·공개/판매중지·삭제 작업을 보여준다.

복제는 리뷰·평점·판매순위를 복사하지 않고 `상품명 (복사본)`, 재고 0, 초안 상태로 만든다. 카테고리 템플릿은 필드 구조만 준비하며 건강 효능 문구를 자동 생성하지 않는다.

## 오류와 안전

- 업로드 실패는 작성 내용을 잃지 않고 파일별 재시도를 제공한다.
- 자동저장 실패는 명확히 알리고 수동 재시도한다.
- 페이지 이탈 시 저장되지 않은 변경이 있으면 확인한다.
- 중복 저장·공개 클릭을 잠근다.
- 공개 전에 이미지, 상품명, 분류, 가격, 재고, 성분·섭취·주의사항을 최종 검증한다.
- Firestore와 Storage 규칙 모두 `admins/{uid}.role == "admin"`을 요구한다.
- 고객은 `productDrafts`와 관리자용 이미지 쓰기에 접근할 수 없다.
- 건강정보 페이지와 상품 템플릿은 검증되지 않은 치료·예방 표현을 생성하지 않는다.

## 복사용 구현 프롬프트

아래 프롬프트를 AI 코딩 도구에 그대로 전달한다.

```text
기존 바이탈리프(VITAL LEAF) 건강기능식품 쇼핑몰 프로젝트를 업데이트해줘. 새 프로젝트를 만들거나 단일 HTML로 다시 작성하지 말고, 현재 저장소의 React 19 + TypeScript + Next.js App Router 호환 Vinext + Firebase 구조와 Sage & Sand 디자인을 그대로 확장해줘.

목표는 두 가지다.
1. 고객에게 보이는 모든 메뉴가 실제 기능·페이지·필터로 연결되어 404나 무반응이 없게 한다.
2. 관리자가 이미지 URL을 복사하거나 긴 폼을 한 번에 작성하지 않고, 단계별로 상품을 임시저장·미리보기·공개할 수 있는 실무형 상품관리 프로그램을 만든다.

작업 전 필수 절차
- 먼저 저장소의 AGENTS.md, README.md, package.json, app/, components/shell/, components/admin/, lib/firebase/, lib/products/, firestore.rules, .openai/hosting.json을 읽어 현재 동작과 테스트 패턴을 파악해라.
- 기존 사용자 변경과 Firebase 설정을 보존하고 관련 없는 리팩터링을 하지 마라.
- 현재 배포 구조를 유지하고 Firebase 상품을 하드코딩된 데이터로 대체하지 마라.
- 각 변경은 실패하는 테스트를 먼저 추가한 뒤 최소 구현으로 통과시켜라.
- 실제 PG 결제와 주문 저장은 이번 작업에서 구현하지 마라. processPayment 교체 경계를 유지해라.

1. 모든 메뉴 기능 완성
- 헤더 로고, 검색, 관리자, 장바구니, 전체 카테고리, 베스트, 오늘의 특가, 건강 고민별, 선물세트, 성분 가이드를 모두 동작시켜라.
- 메가메뉴의 상품 카테고리, 건강 고민, 30대·40대·50대+, 첫 구매 체험 메뉴를 실제 상품 목록 필터와 연결해라.
- 모바일 드로어도 데스크톱과 동일한 메뉴·검색 기능을 제공하고, 열기·닫기·Escape·포커스 트랩·포커스 복원을 유지해라.
- 푸터에는 실제 라우트가 있는 브랜드 소개, 고객센터, 배송 안내, 교환·반품 링크를 제공해라.
- `/story`, `/help`, `/help/shipping`, `/help/returns`, `/ingredients` 페이지를 전문 쇼핑몰 수준으로 구현해라. 배송·교환 문구는 운영자가 한곳에서 수정할 수 있는 설정 상수로 분리해라.
- 성분 가이드는 일반 정보, 확인할 항목, 관련 상품 링크, 건강정보 면책문구를 제공하되 질병 치료·예방 또는 검증되지 않은 효능을 단정하지 마라.
- `lib/navigation/storefront-menu.ts` 같은 단일 메뉴 설정을 만들고 헤더·메가메뉴·모바일·푸터가 이를 공유하게 해라.
- 카테고리와 건강 고민 상수는 관리자 상품 폼도 공유하게 해 메뉴 값과 Firestore 값이 어긋나지 않게 해라.
- `/products`가 `q`, `sort`, `promotion`, `view`, `category`, `concern`, `age`, 가격, 재고 쿼리를 실제 결과에 반영하게 해라. 활성 메뉴에 맞는 제목·설명·결과 수·필터 칩·빈 상태를 보여줘.
- 모든 노출 링크를 순회해 존재하지 않는 라우트나 지원하지 않는 쿼리가 없는지 검증하는 테스트를 추가해라.

2. 관리자 정보 구조
- 기존 Firebase Authentication 이메일/비밀번호와 `admins/{uid}`의 `role: "admin"` 권한 검사를 유지해라.
- 관리자 대시보드를 `판매 상품`, `임시저장`, `CSV 일괄관리` 중심으로 정리해라.
- 상품명, Firestore 문서 ID, 카테고리 검색과 공개·초안·품절 필터, 최근 수정순 정렬을 제공해라.
- 각 상품 행에 썸네일, 상품명, 상태, 가격, 재고, 마지막 수정 시각, 편집, 복제, 미리보기, 공개/판매중지, 삭제 버튼을 제공해라.
- 저장·공개·삭제 중에는 중복 실행을 막고 성공 또는 실패 결과를 접근 가능한 토스트/상태 메시지로 보여줘.

3. 4단계 상품 등록 마법사
- 기존 긴 단일 폼을 다음 단계로 분리해라.
  1) 기본 정보: 상품명, 자동 slug, 카테고리, 건강 고민, 설명
  2) 이미지: 직접 업로드, 대표 이미지, 순서, 대체텍스트
  3) 성분·섭취 정보: 핵심 효능, 반복 가능한 성분표, 섭취법, 원산지, 인증, 주의사항
  4) 판매 정보: 판매가, 정상가, 재고, 베스트, 신상품, 특가와 공개 전 점검
- 단계 표시기, 이전·다음, 임시저장, 미리보기, 판매 공개 버튼을 제공해라.
- 단계 이동은 자유롭게 허용하되 판매 공개는 필수 항목 전체가 유효할 때만 허용해라.
- 오류 메시지는 해당 입력과 aria-describedby로 연결하고 첫 오류 필드로 포커스를 이동해라.
- 모바일에서는 입력창을 한 열로 표시하고 하단에 이전·다음·임시저장 작업 바를 고정하되 safe-area를 고려해라.
- 상품명으로 slug를 자동 생성하되 관리자가 수정한 뒤에는 덮어쓰지 마라. 공개 상품 링크는 계속 Firestore 문서 ID를 사용해라.

4. Firebase Storage 이미지 직접 업로드
- Firebase Storage SDK를 사용해 드래그앤드롭과 파일 선택 업로드를 구현해라.
- 허용 형식은 JPEG, PNG, WebP이고 파일당 최대 10MB로 제한해라. 잘못된 파일은 업로드 전에 이유를 표시해라.
- 경로는 `products/{productId}/{충돌하지 않는 파일명}`으로 제한하고 사용자가 입력한 전체 경로를 그대로 신뢰하지 마라.
- `uploadBytesResumable`로 파일별 진행률, 업로드 취소, 실패, 재시도를 제공해라.
- 첫 번째 성공 이미지가 대표 이미지가 되게 하되 관리자가 다른 이미지를 대표로 지정할 수 있게 해라.
- 이미지 미리보기, 드래그 순서 변경, 대체텍스트, 삭제를 제공해라. 대표 이미지를 삭제하면 다음 이미지를 자동 지정해라.
- 새 표준 미디어 구조는 `media: { url, storagePath, alt, order }[]`로 설계해라.
- 기존 `thumbnailUrl`과 `images: string[]` 문서를 계속 읽을 수 있도록 normalize 계층에 하위 호환 처리를 추가하고 안전한 저장/마이그레이션 방식을 테스트해라.
- 초안 폐기나 상품 삭제 시 해당 상품에서만 사용하는 Storage 파일을 정리하되 다른 상품이 참조하는 파일은 삭제하지 마라.

5. 임시저장·미리보기·판매 공개
- 공개 상품은 기존 `products` 컬렉션에 유지하고, 작성 중 데이터는 별도 `productDrafts` 컬렉션에 저장해 고객에게 절대 노출되지 않게 해라.
- 새 상품 시작 시 안정적인 draft/product ID를 먼저 생성해 이미지 경로와 문서 ID가 계속 같게 해라.
- 입력 변경 후 약 1.2초 디바운스로 `productDrafts/{id}`에 자동저장하고 `저장 중`, `저장됨`, `저장 실패·재시도` 상태를 표시해라.
- 자동저장 실패로 폼 내용을 지우거나 화면을 닫지 마라.
- 공개 상품을 수정할 때는 같은 ID의 수정 초안을 만들고, 작업 중에는 기존 공개본을 계속 고객에게 보여줘.
- `/admin/products/preview/{draftId}` 또는 동등한 관리자 전용 미리보기에서 실제 상품 상세 컴포넌트를 재사용해 데스크톱·모바일 모습을 확인하게 해라.
- 판매 공개 시 전체 검증 후 Firestore batch/transaction으로 `products/{id}`를 생성 또는 교체하고 초안을 정리해라.
- 판매중지는 현재 공개 상품을 초안으로 보존한 후 `products/{id}`를 제거하는 명시적 확인 흐름으로 구현해라.
- 페이지 이탈 전에 저장되지 않은 변경이 있으면 확인하고, 저장된 초안은 나중에 이어서 편집할 수 있게 해라.

6. 빠른 등록 기능
- 기존 상품 복제 기능을 추가해라. 복제본은 리뷰, 평점, 리뷰 수, 판매순위를 복사하지 않고 `상품명 (복사본)`, 재고 0, 임시저장 상태로 생성해라.
- 비타민, 유산균, 오메가3 템플릿은 필요한 입력 그룹만 준비하고 효능·치료 문구를 자동 생성하지 마라.
- CSV 템플릿, UTF-8 BOM, 미리보기, 전체 오류 차단, 최대 400개 제한과 수식 주입 방어 등 기존 안전장치를 유지해라.
- CSV 가져오기도 먼저 초안으로 저장하고 관리자가 검토 후 일괄 공개할 수 있게 해라. 기존 공개 상품을 문서 ID 없이 임의 덮어쓰지 마라.

7. 보안 규칙
- `firestore.rules`에 `productDrafts`는 명시적인 `admins/{uid}.data.role == "admin"` 사용자만 읽기·쓰기가 가능하도록 추가해라.
- `products`는 공개 읽기와 관리자 쓰기라는 기존 계약을 유지해라.
- `storage.rules`를 추가해 `products/{productId}/**` 업로드·삭제는 로그인한 명시적 admin만 가능하게 해라.
- Storage 규칙에서도 파일 크기 10MB 이하와 JPEG/PNG/WebP contentType을 검증해라.
- 관리자 역할 문서가 존재하지만 role이 다른 사용자는 Firestore와 Storage 쓰기를 모두 거부해라.
- Firestore/Storage Emulator 계약 테스트를 추가하고 README에 JDK/CLI 버전, 규칙 테스트와 게시 절차를 정확히 기록해라.

8. 접근성·오류 처리·디자인
- 기존 Sage & Sand 색상, Pretendard/Noto Sans KR, 30~50대가 읽기 쉬운 글자 크기와 전문적인 쇼핑몰 밀도를 유지해라.
- 키보드만으로 모든 메뉴, 마법사, 이미지 순서 조정, 모달을 사용할 수 있게 해라. 드래그 기능에는 위/아래 이동 버튼도 제공해라.
- 로딩, 빈 상태, 권한 없음, 네트워크 실패, 업로드 실패, 중복 제출 상태를 각각 명확히 구분해라.
- `role=status`, `role=alert`, 포커스 이동, 모달 포커스 트랩과 복원을 올바르게 적용해라.
- 건강기능식품 인증 마크나 효능을 실제 자료 없이 임의로 생성하지 마라.
```
